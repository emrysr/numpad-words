# Reusing `src/App.vue` as a component

`src/App.vue` is just the widget itself (the screen + keypad, root element a plain
`<div>`) - the demo page's chrome (header, tips dialog, footer) lives in `index.html`
as static markup plus `src/tips.ts` for the tips dialog's open/close wiring, not in
the Vue component. A host page owns its own landmarks (e.g. `<main>`) around the
component; the component doesn't render one itself, so embedding it doesn't risk a
document ending up with more than one.

There's no npm install for the component yet (see the README's "Publish as an npm
package" item under Future improvements) - until then, reuse means copying/importing
`src/App.vue` (plus `src/lib/*` and `public/trie.json`) directly into a host project.
This doc covers the parts of its public surface that are meant to be depended on: the
`v-model`, and the keypad button customization props/slot.

## Reading the composed text: `v-model`

The component emits `update:modelValue` every time the composed sentence changes,
including once immediately on mount with `''`. That makes it a normal `v-model`
target:

```vue
<script setup>
import { ref } from 'vue'
import Numpad from './App.vue'

const text = ref('')
</script>

<template>
  <Numpad v-model="text" />
  <input type="hidden" name="message" :value="text" />
</template>
```

There's no prop feeding a value back *into* the component (it isn't a controlled
input) - the numpad always owns its own composition state internally; `v-model`
here is one-way out, for reading/storing the result (e.g. into a hidden form field
before submit), not for programmatically setting the text.

## Restyling the keypad buttons

The 4x3 grid itself (`KEYPAD_ROWS`) and its layout CSS are intentionally not
configurable - the arrangement (`1 2 3` / `4 5 6` / `7 8 9` / `* 0 #`) is a fixed
invariant of the interaction model, not something a consumer should be able to
break. What *is* configurable is how each button looks and what it renders inside.

### Class props

Three optional props that layer together rather than replace each other:

| Prop | Applies to |
|---|---|
| `buttonClass` | every key. Defaults to `'button is-rounded is-flex-direction-column'` (today's Bulma-based look) |
| `numberButtonClass` | digit keys `0`-`9`, *in addition to* `buttonClass` |
| `symbolButtonClass` | `*` and `#` (pure control keys - cycle/manual-toggle and delete/clear - with no digit meaning of their own), *in addition to* `buttonClass` |

Each accepts anything Vue's `:class` binding accepts (a string, an array, or an
`{ className: boolean }` object). `numberButtonClass`/`symbolButtonClass` are added
on top of `buttonClass`, not swapped in for it - a number key gets both `buttonClass`
and `numberButtonClass` together, so `buttonClass` is the shared base to put anything
common in (padding, transitions, a design system's base button class), and the other
two are for what should differ between the two key families:

```vue
<Numpad
  button-class="key-btn"
  symbol-button-class="key-btn--control"
/>
<!-- 0-9 render class="key-btn"; */# render class="key-btn key-btn--control" -->
```

To fully replace the default look instead of layering onto it, set `buttonClass`
itself (it has no separate default to fall back to once overridden) rather than
leaving it at its default and trying to override it via the other two.

### The `#button` slot

By default each key renders its digit label (letters for `2`-`9`, punctuation
preview for `1`, `space`/`save` for `0`, `next`/`del` for `*`/`#`) above the raw
digit. To render something else, use the scoped `button` slot:

```vue
<Numpad>
  <template #button="{ digit, label, isSymbol }">
    <span :class="{ 'is-symbol': isSymbol }">{{ label }}</span>
  </template>
</Numpad>
```

Slot props:

- `digit: string` - the key's own character (`'0'`-`'9'`, `'*'`, or `'#'`).
- `label: string` - what the default rendering shows above the digit.
- `isSymbol: boolean` - `true` for `*`/`#`, `false` for `0`-`9`.

The slot replaces only the button's *inner content*. The `<button>` element itself,
its grid placement, and its `pointerdown`/`pointerup`/`pointerleave` handlers (long-
press detection, digit entry, cycling, etc.) stay owned by the component - a custom
slot can't accidentally break interactivity or drop a key from the tab order by
forgetting to wire up an event handler.

## Sizing hook: CSS custom properties

`--font-lg`/`--font-sm` (set on the `.device` wrapper) drive every font-size in the
component - the keypad digit, the sentence display, the candidate tags, all of it.
Because custom properties inherit through the DOM regardless of Vue's `<style
scoped>` boundary, a host page can override them from outside without touching the
component's own styles:

```css
/* in the host page's own stylesheet */
.device {
  --font-lg: 2rem;
  --font-sm: 1.25rem;
}
```

## What's not exposed yet

Everything else - colors, spacing, the sentence/candidate-tag markup, the tips
dialog - is still fixed, Bulma-derived, scoped CSS. Extending the same
prop/slot/CSS-variable pattern used above to those areas is future work, not
something already wired up.
